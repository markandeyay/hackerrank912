## Inconsistencies and fixes

None found. Every category above is handled by a general rule and the outputs agree with both the statement and the
documented assumptions (notes/mismatches.md items 6-9). Observations worth recording, none of which needs a code change:

* Case 5 is the only place where a different reading would move decisions (request_145, 241, 256 under
  `n * frequency / 30 <= max`). The current one-payment-one-month definition is kept: the statement calls the cap
  "months", options are monthly cadences, and the 3 x 31-day offers are the seller's "3 months" plan.
* Case 9's `earliest_date_for_full_payment == request_date` next to `not_affordable` (request_251) follows the
  statement's "measures financial capacity independently of the user's payment-method preferences"; the explanation
  already says the full amount is safe but no accepted method can deliver it.
* Cases 6 and 11 are empty on the hidden set; the code paths (`earliest <= desired`, `max(sd, rq)`) are covered by the
  unit tests in `code/tests/` only.
